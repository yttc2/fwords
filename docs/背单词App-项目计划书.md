# 背单词 App · 项目计划书

**版本** v0.1 · 2026-09-21
**阶段** 阶段一：Web Demo（机制验证） → 阶段二：Android 应用

---

## 0. 一句话概括

一个「边学边短时回顾」的背单词应用：词库切成 10 份逐份推进，学习过程自动计时；每学满 6 个词、每 5 分钟、每 30 分钟各触发一次回顾，回顾期间计时暂停，回顾结束后继续；进度自动保存，下次打开回到上次的位置。

核心差异化不在于「词库大」，而在于**把遗忘曲线压缩到一次学习会话内部**——不靠第二天再复习，而是当场在 5 分钟、30 分钟这两个关键节点把刚学的词拉回来过一次。

## 3. 核心机制设计

### 3.1 分组规则

分组**优先按词表自带的分节**，没有分节才均分十份。

**① 词表带分节（如「十天搞定考研词汇」的 Day 1 ~ Day 10）**

- 分节能**完整覆盖全部词**（各节词数之和 = 总词数）→ **按分节分组，一组 = 一节**
- 分节残缺或只有 1 节 → 视为不可信，**退回均分十组**

> 为什么要求「完整覆盖」：如果某天的标题漏了一行，解析出来的分节就是残缺的。这时按它分组会给出一个错的结构（比如本该 10 天却只有 9 天），而错的分组比「均分十组」更糟 —— 用户会以为自己在按书背，实际上天数和书对不上。

**② 无分节 → 均匀切成 10 份**

设词库共 N 个词：

- N ≥ 10：`base = floor(N / 10)`，`rem = N % 10`；前 `rem` 组每组 `base + 1` 个词，其余每组 `base` 个词
  - 例：N = 120 → 10 组 × 12 词；N = 47 → 7 组 × 5 词 + 3 组 × 4 词
- N < 10：降级为 N 组，每组 1 词，UI 上提示「词库过小，分组已调整」
- N = 0：引导用户先导入词表

> 注意不要用 `ceil(N / 10)`：N = 12 时 `ceil` 会算出每组 2 词、只有 6 组，与「分成 10 份」的要求不符。均匀分配才能恒得 10 组。

**③ 单独载入某一节**

词库页会为每个分节渲染一个 chip（`Day 1 · 505词`）。点它表示「今天只背这一天」，此时该节**整体作为一个学习单元**（1 组）。

T1 的 6 词单元不按「组内切片」绑定，而是**按全局已学流水取最后 6 个**。这样即使用户在组之间跳转，T1 回顾的永远是「最近学过的 6 个词」。

### 3.2 状态机与计时

应用只有三个顶层状态：

```
IDLE  ──开始背诵──▶  LEARNING  ──触发回顾──▶  REVIEWING
                        ▲                        │
                        └────── 回顾结束 ─────────┘
```

**计时原则：只有 LEARNING 状态累加计时。**

这里有一个关键设计决策：

> **时间轴用「净学习时长」而不是墙上时钟（wall clock）。**

原因：回顾期间不计时。如果用 `Date.now()` 做时间轴，回顾花掉的 3 分钟会把「5 分钟窗口」撑满，导致刚结束 5 分钟回顾、立刻又触发一次 T2 回顾。用净学习时长（`netStudyMs`）做时间轴，回顾被天然排除在外，逻辑自洽且不会误触发。

实现要点：

- 用 `performance.now()` 记录进入 LEARNING 的时刻，退出时把差值累加到 `netStudyMs`，**不要用 `setInterval` 累加计数**（会因页面卡顿、切后台而漂移）
- 显示用的秒表可以用 `setInterval(250ms)` 渲染，但真实数值只认差值累加
- 页面刷新 / 切后台后，按「离开时的状态 + 时间戳」恢复：若刷新发生在 LEARNING 中，离开的这段时间**不计入**（因为无法确认用户是否真的在学），从刷新后重新开始计时

### 3.3 三种回顾触发

三个独立的计时器 / 计数器并行运行：

| 触发 | 判定条件 | 回顾内容 |
|------|----------|----------|
| **T1** 词数触发 | 本组已学词数 `% 6 == 0` 且 > 0 | 刚学完的这 6 个词 |
| **T2** 短时触发 | 自上次 T2 起，净学习时长 `≥ 5 分钟` | 最近 5 分钟净学习时长内学过的所有词 |
| **T3** 长时触发 | 自上次 T3 起，净学习时长 `≥ 30 分钟` | 最近 30 分钟净学习时长内学过的所有词 |

配套要记录的数据：

- `wordsSinceLastT1`：距离上次 T1 已经学了几个词
- `msSinceLastT2`、`msSinceLastT3`：两个时长计数器
- `learnedLog: [{ wordId, atNetMs }]`：按净学习时长打点的「已学流水」，T2/T3 靠它反查窗口内容

### 3.4 边界处理（已定稿）

**① 触发时机：软触发（已确认）**

5 分钟到了，用户正在看第 7 个词 —— **不打断**。顶部亮一条提示「已到回顾节点（T2 · 每 5 分钟，N 个词）· 切到下一个词后自动开始回顾」，等用户自己点/滑到下一个词时，才进入回顾。

硬打断体验割裂，用户会觉得自己被抢了操作权。软触发让节奏掌握在用户手里，代价只是回顾晚几秒开始。

**② 窗口内词数太少：不做限制（已确认）**

窗口里只有 2 个词也照常回顾。宁可贵在「准点」，也不要为了凑数把回顾推迟到不确定的时刻 —— 推迟会让整个节奏失去可预期性。

**③ 三种回顾内容重叠：不去重（已确认）**

T1 刚回顾完的 6 个词，如果紧接着 T2 又覆盖到，就再做一遍。短时间内重复接触本身就是这个机制想要的效果，不额外做冷却期。

**唯一保留的「去重」是计数器语义上的，不算冷却期：**

- 完成 T1 → `t1Baseline = learnedLog.length`（重新数 6 个）
- 完成 T2 → `lastT2AtNetMs = netStudyMs`
- 完成 T3 → `lastT3AtNetMs = lastT2AtNetMs = netStudyMs`

最后一条是必要的：**T3 的 30 分钟窗口在集合意义上包含 T2 的 5 分钟窗口**，既然刚做完 T3，把 T2 也一起复位是计数器的正确语义，否则会立刻再弹一次内容被 T3 完全覆盖的 T2。

**④ 同时到期的优先级：T3 > T2 > T1**

同一时刻只进一个回顾，做完后重新判定，剩余的依次排队执行（不做内容合并）。

### 3.5 回顾模式交互（已定稿）

- 一次只显示一张卡，**先只显示单词**（不给释义），用户尝试回忆
- **不判断「认识 / 不认识」** —— 回顾是「再过一遍」，不是「考试」。翻面看完就往下走，不做任何标记
- 交互（三条路径等价，视设备而定）：
  - **点击卡片**：未翻面 → 翻出释义；已翻面 → 前进到下一个
  - **按钮「下一个」**（最后一张变「完成回顾」）
  - **左滑 = 下一个，右滑 = 上一个**（右滑回看，不计入任何计数）
- 顶部进度条显示本次回顾还剩几张
- 结束后给一个结果页：本次回顾了哪 N 个词（中性罗列，不做「对/错」评判），以及这一段回顾花了多久
- **整个回顾过程计时暂停**，回顾结束后回到学习页，计时从原值继续累加

> 为什么去掉标记：老板明确要求。回顾的目的是**重复曝光**，标记会引入「我在测试自己」的压力，也迫使每张卡多按一次；去掉后回顾的节奏明显更顺。代价是失去了「不熟词优先重排」的数据来源 —— 如果以后想要，可以从 `progress[id].review` 的累计次数反推（看同一个词被回顾了几次），不必让用户手动标。

### 3.6 记忆环节交互

卡片正面内容（自上而下）：

```
┌─────────────────────────┐
│  [ 🔊 ]          3 / 12 │   ← 发音按钮 + 组内进度
│                          │
│      abandon             │   ← 单词（大字）
│      /əˈbændən/          │   ← 音标
│                          │
│   ── 点击显示释义 ──      │   ← 释义默认隐藏，点击展开
│                          │
│   ← 上一个    下一个 →    │   ← 或直接左右滑动
└─────────────────────────┘
```

- **释义默认隐藏还是显示**：待定（见第 9 节 Q7）。默认隐藏更能强迫回忆，但学习阶段可能太累。建议学习环节默认显示、回顾环节默认隐藏
- 手势：左滑 / 点击卡片右半区 = 下一个；右滑 = 上一个；上滑 = 标记「已掌握，跳过」
- 发音：`autoPlay` 开关打开后，每次切词自动读一次
- 底部常驻一个瘦长状态条：`已学 12 · 净学习 04:37 · 距下次回顾 00:23`

### 3.7 断点续背

需要持久化的完整会话快照（每次状态变更后写入，或至少每 2 秒节流写入一次）：

```json
{
  "version": 1,
  "wordListId": "default",
  "groupIndex": 2,
  "cursorIndex": 7,
  "netStudyMs": 277000,
  "phase": "learning",
  "counters": { "wordsSinceLastT1": 1, "msSinceLastT2": 96000, "msSinceLastT3": 277000 },
  "learnedLog": [{ "wordId": "w013", "atNetMs": 271000 }],
  "progress": { "w013": { "studyCount": 2, "reviewCount": 1, "lastReviewedAtNetMs": 260000, "flags": ["hard"] } },
  "savedAt": 1758456800000
}
```

下次打开时读取该快照；若 `phase == "reviewing"`，恢复为「回到学习页 + 队列里那次待做的回顾重新做一遍」（因为回顾被打断，状态不可靠，重做更安全）。

## 4. 数据模型

| 实体 | 字段 |
|------|------|
| **Word** | id, text, phonetic, meaning, example?, audioUrl? |
| **WordList** | id, name, words[], createdAt, groupCount |
| **WordProgress** | wordId, studyCount, reviewCount, lastStudiedAtNetMs, lastReviewedAtNetMs, flags(known / hard / mastered) |
| **Session** | id, wordListId, groupIndex, cursorIndex, netStudyMs, phase, counters, learnedLog[], savedAt |
| **ReviewLog** | id, sessionId, type(T1/T2/T3), wordIds[], startedAtNetMs, endedAtNetMs, knownCount, hardCount |

存储方案：

- Web Demo：`localStorage`（单 key 存整个状态树 JSON，够用且零依赖）
- Android：Room（SQLite）+ DataStore（存会话快照）

## 5. 技术选型

### 5.1 Web Demo

| 方案 | 说明 | 评价 |
|------|------|------|
| **A. 原生 HTML + CSS + JS**（推荐） | 单页多文件，无构建步骤，`localStorage` 持久化，Web Speech API 发音，双击 `index.html` 即可运行 | ✅ Demo 的目的是验证机制和手感，不是验证工程架构。零构建意味着改一行刷新就能看到，迭代最快 |
| B. Vite + React + TS | 组件化、状态管理规范 | 引入构建步骤和依赖。如果确定后续要用 Capacitor 打包并长期维护，可以选它 |

**决定：方案 A（原生 HTML + CSS + JS，零构建）。** 理由：机制还没定型，任何框架抽象都是负担；改一行刷新就能看到效果，迭代最快。

### 5.2 Android

**决定：方案 A（Kotlin + Jetpack Compose + Room + TextToSpeech），不套壳。**

| 方案 | 说明 | 结论 |
|------|------|------|
| **A. Kotlin + Jetpack Compose + Room + TextToSpeech** | 全原生 | ✅ **采用**。体验最好、技术深度最高——Room 数据库、状态机、TTS 引擎、Compose 声明式 UI 都是可写进论文的实打实技术点 |
| B. Capacitor / WebView 套壳 | 复用 Web Demo 代码 | ❌ 已排除。虽然工作量最小，但「套壳」在评审里通常会被追问「技术贡献在哪」 |
| C. Flutter | 跨平台 | ❌ 已排除。和 Web Demo 不共享代码，等于重写一遍 |

Web Demo 的角色因此明确为**机制验证与交互原型**，不作为 Android 端代码基座。迁移时以它的行为为准逐条复刻，而不是搬运代码。

### 5.3 语音方案

| 场景 | 方案 |
|------|------|
| Web Demo | Web Speech API `speechSynthesis`，设置 `lang = 'en-US'`，挑一个本地音色。零成本，音质取决于系统 |
| Android | 原生 `TextToSpeech` + 离线语音包（Google TTS 或讯飞）；若要音质统一，改用预录 MP3 + `ExoPlayer` |

> 注意：浏览器 `speechSynthesis` 各平台音色差异很大，且部分浏览器需要用户先交互才允许播放。demo 阶段建议在首次点击时初始化一次。

## 6. 页面结构

| 页面 | 内容 |
|------|------|
| **首页 Home** | 「继续背诵」/ 分组进度格子（10 天或 10 组，带分节名）/ 累计统计 / 从头重来 |
| **词库页** | 词库下拉、按分节载入（点某一天）、批量取词、粘贴导入、选文件导入 |
| **学习页 Study** | 单词卡片、进度条、发音按钮、净学习计时器、回顾倒计时提示条 |
| **回顾页 Review** | 回顾类型标签（6 词 / 5 分钟 / 30 分钟）、卡片、翻面看释义、「下一个」（无标记按钮） |
| **结果页 Summary** | 本次回顾词数、回顾词列表（中性罗列）、本组总耗时、下一组入口 |
| **调试页 Debug** | 时间加速 ×60、回顾机制开关、各计数器实时值、重置 |

页面之间是单向流程，只有「学习页 ⇄ 回顾页」是往复的。

## 7. 里程碑

### M1 · Web Demo 骨架
- 词库导入 + 自动分 10 组
- 学习页卡片：点击/滑动切词、发音按钮
- 净学习计时器（含暂停/恢复正确性）
- `localStorage` 存快照 + 冷启动恢复
- **验收：刷新页面能回到原单词、计时器数值不跳变**

### M2 · 三重回顾机制
- T1（6 词）、T2（5 分钟）、T3（30 分钟）触发逻辑
- 三种回顾内容取数（含净学习时长窗口）
- 回顾暂停计时 / 结束恢复计时
- 时间加速调试开关（把 5 分钟压成 5 秒来测）
- 冲突与边界处理（第 3.4 节的三个问题落地）
- **验收：能在 1 分钟内完整走完一次 T1→T2→T3 的模拟流程**

### M3 · 记忆状态与统计
- 每个词的 studyCount / reviewCount / flags 记录
- 「不熟」词的下轮优先
- 结果页统计
- 进度条与整体完成度

### M4 · Android 迁移
- 技术选型定稿 → 工程搭建
- UI 用 Compose 复刻（视觉可重设计，交互保持一致）
- Room 落库，替换 localStorage
- 原生 TTS 替换 Web Speech API
- 打包签名、真机测试（含切后台、锁屏、来电中断）

### M5 · 打磨
- 空态 / 异常态 / 断网态
- 长词库性能（1000+ 词）
- 无障碍与动效

## 8. 验收与边界用例清单

写代码前先把这些用例记下来，每一个都是真机上一定会遇到的：

| # | 用例 | 期望行为 |
|---|------|----------|
| 1 | 词库 47 个词（不是 10 的倍数） | 每组 5 词，最后一组 2 词，不丢词 |
| 2 | 词库只有 4 个词 | 降级为 4 组，给出提示 |
| 3 | 一个词停了 6 分钟才切下一个 | T2 到点但窗口内词数不足 → 按 Q2 的规则顺延 |
| 4 | 5 分钟和 6 词同时触发 | 按 Q3 规则处理，不重复回顾同一批词 |
| 5 | 回顾中刷新页面 | 恢复到学习页，待做回顾重新入队 |
| 6 | 学习 2 分钟后切后台 10 分钟再回来 | **不触发** T2/T3（净学习时长只有 2 分钟） |
| 7 | 全部背完 | 显示完成页，提供「重新开始 / 下一份词库」 |

## 12. 词库方案

### 12.1 数据源

**考研词汇 5047 词**，取自开源仓库 [KyleBing/english-vocabulary](https://github.com/KyleBing/english-vocabulary)
的 `full_line_jsonl/sentence/正序/考研.jsonl`（原始 9602 行，按单词去重后 5047 个）。

| 项 | 情况 |
|---|---|
| 字段 | 单词、美/英音标、多条带词性的释义（原库还含词组与例句，Demo 阶段未收录以控制体积） |
| 音标覆盖 | 5038 / 5047（9 个词源数据本身缺音标，**未自行编造填补**） |
| 生成方式 | `tools/build_wordlist.py` → `demo/wordlists.js`（393 KB，含两个入口共用同一份 raw） |
| 许可 | 开源仓库，用于学习用途 |

### 12.1.1 两个词库入口

| 入口 | 用途 |
|---|---|
| `kaoyan10` **（默认）** | 同一批词切成 **10 天**（Day 1~10，每天 505 / 504 词）。选它就是「十天背完」，首页直接显示 10 个格子 |
| `kaoyan` | 整份 5047 词。按词数**分批取**（默认每次 60 词），适合「每天背一点、逐批推进」 |

`kaoyan10` 的 `raw` 与 `kaoyan` **指向同一个数组**（在 JS 里用 IIFE 里的局部变量共享），所以两个入口并存不会让文件翻倍 —— 393 KB 而不是 786 KB。

两者对**学习状态体积**的影响差别很大（已实测，口径为 JS 字符数 —— localStorage 配额也按这个算）：

| 入口 | 载入方式 | `state.words` 词数 | 存档体积 | 占 5 MB 配额 |
|---|---|---|---|---|
| `kaoyan10` | 一次全部 | 5047 | **446 K 字符** | ~9% |
| `kaoyan` | 分批 60 | 60 | 5 K 字符 | ~0.1% |

446 K 是这套设计里最大的一笔开销，来自「按天自由跳转」这个需求 —— 要跳转就得让 10 天的词都在内存里。它远低于配额上限，低端机上约 15~20 ms/秒的序列化开销，可接受但不算宽裕。因此保留 `kaoyan` 作为「轻量模式」，一键可切，并在测试里对两个数字都设了断言（防止以后悄悄变差）。

### 12.1.2 导入自己的电子词表

详见 `docs/词库导入指南.md`。三条通道：

| 路径 | 适用 | 要不要重新部署 |
|---|---|---|
| 网页端「自定义词表」 | txt / csv / tsv / json / md，几千词以内 | 不用，刷新即可 |
| `tools/import_words.py` + **只给词的顺序** | 音标与释义由内置开源词库按拼写配对补全（实测 100%） | 要（重新打包上传） |
| `tools/import_words.py` + 完整文件 | xlsx / docx / **ppt·pptx 课件** / 书版自然排版 / 大文件 / 需要精确分节 | 要 |
| `tools/mobi_words.py` + **正版电子书** | `.mobi` 直接抽音标 + 释义 + List 归属，**最完整的一条** | 要 |

命令行导入**不依赖任何第三方库** —— xlsx 和 docx 本质是带 XML 的 zip，用标准库直接读；旧版 .ppt 是 OLE2 复合文档（`D0CF11E0` 开头），按 [MS-CFB] / [MS-PPT] 公开规范自己实现扇区链与记录流解析（`tools/ppt_extract.py`）；MOBI 电子书按 PalmDB + PalmDOC 规范自己解（`tools/mobi_extract.py`）。全部零依赖 —— 本机 pip 拉不到包的情况下也能用。

**书版自然排版**（词条跨多行、夹着考点与例句）按这套规则解析，已固化成回归测试（整套 194 项）：

| 规则 | 说明 |
|---|---|
| 单词只取行首 | `abandon /əˈbændən/ vt. 抛弃` → 单词是 `abandon` |
| 音标从行尾抠 | `/…/`、`[…]`、裸音标 token |
| `【…】` 标注行整行丢弃 | 考点搭配 / 例句 / 记忆法 / 派生 |
| 释义续行回接 | `n. 账户；描述` 接到 `account`，不变成新词条 |
| 词性行不是词条 | `vt. 加速，促进` 不会被当成单词 |
| 多词级释义合并 | 同词多次出现，释义合并为一条 |

**List → Day 折叠**：`--per-day N`（默认 2）把每 N 个 List 合成一天。分节本身已是 Day 时原样使用（不二次折叠）；不能整除时不折叠 —— 宁可不折，不要错折。

导入结果累积在 `data/user-libs.json`，`demo/wordlists.user.js` 每次整份重新渲染，所以多次导入不会互相覆盖。

### 12.1.3 王江涛《十天搞定考研词汇》

| 项 | 情况 |
|---|---|
| 单元结构 | **20 个 List，分 10 天**，每天 2 个 List（Day 1 = List 1-2 … Day 10 = List 19-20） |
| 考频分级 | 五星词汇 List 1-2 / 四星词汇 List 3-6 / 三星词汇 List 7-20 |
| 词量 | 约 4600 词 |
| 词条内容 | 音标、中文释义、记忆方法、真题例句、考点搭配、派生词 |

**数据来源的现实**：这是正版商业出版物（浙江教育出版社，第 3 版 2024），**没有合法的公开词表数据源**，也不去扒盗版站点。受保护的是作者写的释义、真题例句、记忆方法与整本书的编排；单词本身来自考研大纲，是公开的。

**已落地做法**：老板提供了**正版电子版（MOBI）**，走 `tools/mobi_words.py` 直接抽取。

| 项 | 实测结果 |
|---|---|
| 抽出词量 | **2881 词**（20 个 List 原样保留，折成 10 天） |
| 音标覆盖 | **2881 / 2881（100%）** |
| 释义覆盖 | **2881 / 2881（100%）** |
| 与书末索引比对 | 索引 2880 词逐条校验，差异仅 **9 处**（4 + 5），全部可解释：英式拼写 `fulfill`/`organization`、只在词组里出现的 `trade`、索引自身漏收的 `editor`/`jaw`/`learning`、以及因书中笔误 `+office` 而漏抽的 `officer` |
| 抽取策略 | **以音标行为锚**（`/ … /` 是全书最稳定的结构信号），往上定词头、往下收释义 |

**备选做法（未采用）**：只取**词的顺序**（哪个词在哪个 List / 第几天），音标与释义从开源考研词库按拼写配对补全，得到「书的进度结构 + 合法来源的释义」。在拿到电子版之前是首选方案，现留作后备。

**核对手续**：抽取结果会另出一份**核对稿**（按 Day / LIST 分组逐词列出 + 与索引的差异比对 + 人工备注），供人工过目。工具对**疑似印刷错误**（例：某派生词条印成 `+office`，但音标 `/ˈɔːfisə/` 与释义都指向 `officer`）**原样保留、不擅自改**，只在备注里标出。

**部署注意事项**：站点挂在公网域名上。把自己的电子书内容整份放进去等于向公众分发，与个人本地自用性质不同。约定：**书版词库只在本地使用**，线上继续用内置开源考研词库；如需上线，给站点加宝塔的「访问限制」（密码访问）。


### 12.2 为什么没用墨墨背单词的 API

墨墨**确实有**官方开放 API（`open.maimemo.com`，2025 年上线），但**不能当词库用**。已逐条核实：

| 事实 | 影响 |
|---|---|
| `GET /vocabulary?spelling=word` 只返回 `{id, spelling}` | 拿不到音标、拿不到释义 |
| `GET /interpretations?voc_id=...` 返回的是**用户自己创建的释义** | 不是墨墨内置词典内容 |
| 没有「拉取某本词书全部单词」的接口 | 整套 API 是围绕「你自己的云词本 / 学习计划」设计的 |
| token 有效期仅 7 天，且必须放在 `Authorization` 头 | **绝不能写进静态页面前端**（F12 即可被拿走） |

**结论**：墨墨 API 适合做**反向同步**（把本 App 里的词推回墨墨的学习计划），不适合做词库来源。本期不做，见第 9 节 Q10。

### 12.3 词库与学习状态的分层（关键设计）

内置词库 5047 词**不能整个放进学习状态** —— 既会撑爆 localStorage（通常 5 MB 限额），每次自动存档还要重复序列化整份词库。

因此分两层：

- **静态词库层**（`wordlists.js` / `wordlists.user.js`）：全量词库，随页面加载，**不参与持久化**
- **本次目标层**（`state.words`）：
  - 词库**有分节**（十天计划）→ 整份载入（5047 词 / 446 K 字符），因为要按天跳转，必须全部就位
  - 词库**无分节** → 用户指定「本次学多少个词」（默认 60 / 5 K 字符），按偏移量取一批

`state.libOffsets[libKey]` 记录已取走的词数，因此**反复载入会一批批往下取**，直到把整个词库背完；取到末尾自动回绕到第 1 词。

这是本方案唯一一处「为了功能牺牲体积」的取舍，已在 12.1.1 量化，并提供可一键切换的轻量入口。
